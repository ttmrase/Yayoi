# バックアップと復元(ユーザー要件 B5)

利用者のデータ(確定した値・切り出し画像・追加学習の世代・設定・税区分の記憶など)を 1 つの zip にし、別の PC・壊れたあとの環境へ戻せるようにする。
バックアップには**帳票の内容(確定した摘要・金額)が含まれる**ので、保管と持ち運びは利用者の責任(画面にも注意を出す)。暗号化はしない(Windows の BitLocker 等に任せる)。

## 何を入れるか

| 内容 | 場所(データ領域 `%LOCALAPPDATA%\yayoi-ocr`) | 備考 |
|---|---|---|
| DB(確定値・設定・税区分の記憶・出力の履歴・世代の記録) | `app.sqlite3` | **SQLite の backup API の整合の取れたスナップショット**を作って入れる(動いている DB のファイルをそのままコピーしない) |
| 切り出し画像・確認画面の縮小画像 | `images/` | |
| 認識の入力(追加学習用) | `pagedata/` | |
| 世代の重み・確信度・メタ | `models/<プロファイル>/gen_XXXX/` | 1 世代 約 70 MB。復元後に重みと確信度の組を全部照合する |
| 出力したファイル | `exports/` | 小さい |
| 取り込んだ元画像(任意) | `uploads/` | 「元画像も含める」を選んだときだけ。大きい |

含めない: 追加学習の作業ディレクトリ(`training/`)、復元の作業用ディレクトリ、バックアップの一時置き場。
元画像を含めないバックアップでは、復元後に**確認前のページの再認識や罫線の再切り出しはできない**(画面に書く)。確定済みのページと学習の元は復元される。

## zip の構成(`FORMAT_VERSION` = 1)

```
manifest.json    形式・版・作成日時・アプリの版・DB のスキーマ版・元画像を含むか・件数・ファイル一覧のハッシュ(小さい JSON。最後に書く)
files.sha256     1 行 1 ファイル: `sha256 サイズ パス`
db/app.sqlite3
images/<ページ>/<セル>.png  images/<ページ>/view.jpg
pagedata/<ページ>.npz
models/<プロファイル>/gen_NNNN/{重み 2 つ, confidence.json, meta.json}
exports/<ファイル名>
uploads/<32 桁の 16 進>/original.<拡張子>      (任意)
```

## 作成

1. 設定画面の「バックアップを作成」(元画像を含めるかを選ぶ)。
2. サーバが DB のスナップショットを作る(DB のロックの下。`sqlite3.Connection.backup`)。
3. **別プロセス**(`backup_worker`)が、データ領域のファイルを zip に書きながらハッシュを計算し、一覧と manifest を最後に書く(途中で止まった zip には manifest が無い)。進捗を画面に出す。
4. できたら「保存する(保存先を選びます)」: **1 回だけ使える合言葉**つきの URL(`/download/backup/<合言葉>`、10 分で失効)を返し、画面が `<a download>` で開く。
   WebView2 の「名前を付けて保存」で保存先を選ぶ(トークンの要る `/api/` はリンクのダウンロードに使えないため。ブラウザにファイル全体を載せない)。
   一時置き場 `backups/` の zip は、「破棄」・次の作成・アプリの終了・次の起動で消す。

**pywebview の `ALLOW_DOWNLOADS`**: pywebview の WebView2 は、この設定が False(既定)だとダウンロードを**何も表示せずに取り消す**(`on_download_starting`)。`launcher.configure_webview` で True にしている
(出力の CSV・精度レポートのダウンロードにも必要。以前の版では実機で取り消されていた可能性がある。Windows の実機チェックリスト E4 で確認)。

## 復元

利用者が持ち込んだ zip と、その中の DB は**信用しない**。サーバのプロセス(トークンと DB を持つ)では解かず、使い捨ての別プロセスで検査・取り出しをする(アップロードの検査 `probe.py` と同じ方針)。

1. 設定画面で zip を選ぶ → サーバが `restore/incoming.zip` に書く(上限 64 GiB + 1 GiB、ディスクの空きを確認)。**認識・追加学習の最中は受け付けない**(409 `busy`)。
2. **検査**(別プロセス): zip の構造・名前・大きさ・圧縮率・manifest・ファイル一覧・全ファイルのハッシュ。通れば要約(日時・ページ数・世代数・大きさ)を画面に出す。
3. 利用者が「置き換える」を確認 → **取り出し**(別プロセス): `restore/staging/` にハッシュを照合しながら取り出し、取り出した DB を検査。通れば「復元の準備ができた」印(`restore/pending.json`)。
4. **アプリを閉じて開き直す**。起動の最初(DB を開く前、`launcher` → `backup.apply_pending`)に入れ替える:
   - いまのデータ(DB・images・pagedata・models・exports・uploads)を `restore-undo/` へ**移して退避**(同じボリュームの名前の付け替えなので速く、容量も要らない)。
   - 取り出したデータを置く。**途中で失敗したら、置いたものを消して退避したものを元に戻す**(`restore-result.json` に失敗のコード)。
   - 退避は直近の 1 回分だけ(次の復元で消える)。画面の「退避したデータを削除」で消せる。
5. 起動後、`gens.check_all` が**全世代の重みと確信度の組を照合**する(壊れていれば `broken` にして警告。使用中の世代が壊れていれば出荷時の組へ戻す)。結果の件数を復元の結果に残し、画面に出す。
6. DB が古い版なら、通常の起動の移行(`db.migrate`)で上がる。新しい版(このアプリが知らない版)は拒否する。

DB を開いたまま入れ替えない理由: Windows ではファイルの入れ替えがロックに阻まれ、開いている接続・実行中のスレッド(認識・学習)が古い DB を見続けるため。入れ替えを起動の最初に寄せると、それらを考えなくてよい。
準備ができたあとでもアプリは使え、その間にできたデータは、入れ替えのとき `restore-undo/` へ退避される(復元の確認の画面にも書く)。

## 検査の中身(悪意のある zip・壊れた zip)

| 検査 | 拒否するコード |
|---|---|
| zip として読めない | `not_a_zip` |
| 名前: 許可リスト(`db/app.sqlite3`、`images/<数>/<数>.png|view.jpg`、`pagedata/<数>.npz`、`models/<数>/gen_<4桁>/<決まった名前>`、`exports/<1 階層>`、`uploads/<32 桁の 16 進>/original.<拡張子>`)。`..`・絶対パス・`\`・`:`・空の成分・Windows の予約名・末尾の `.`/空白・制御文字・`* ? " < > |` | `entry_name_invalid` |
| シンボリックリンク・ディレクトリ・暗号化・deflate/stored 以外の圧縮 | `entry_type_invalid` |
| 大文字小文字・Unicode 正規化だけが違う重複 | `entry_duplicate` |
| 個数 200 万・1 ファイル 16 GiB・合計 64 GiB・圧縮率 200 倍(4 MB 以上のファイル。zip 爆弾) | `too_many_entries` / `entry_too_large` / `total_too_large` / `ratio_too_high` |
| 大きさは申告を信用せず、読んだ実際のバイト数でも数える | `size_mismatch` |
| manifest の形式・版・各項目、スキーマ版が新しい | `manifest_missing` / `manifest_invalid` / `format_unsupported` / `version_unsupported` / `db_too_new` |
| ファイル一覧のハッシュ・一覧と zip の突き合わせ(欠け・余分)・全ファイルのハッシュ | `hash_list_mismatch` / `file_list_mismatch` / `hash_mismatch` |
| DB: 読み取り専用(`immutable`)で開き `PRAGMA integrity_check`、**スキーマが現在の版のスキーマと完全に一致**(余分なテーブル・ビュー・トリガーを拒否)、**ファイルの置き場を指す列が決まった形**(`cells.crop_path` など。`../` で領域の外を読ませない)、世代の `dir` が決まった形 | `db_invalid` / `db_schema_mismatch` / `db_path_invalid` / `db_missing` |
| ディスクの空き(取り出す大きさ + 256 MB) | `disk_full` |

取り出しが失敗したら、取り出したものを全部消す。ログ・状態・結果には、コードと件数と大きさだけを出す(値・パスは出さない)。

## API(すべて `/api/` はトークン必須。ダウンロードだけ合言葉)

`GET /api/backup`(状態: 実行中・進捗・作成済み・検査済み・準備済み・直近の結果・退避)、`POST /api/backup/create`、`POST /api/backup/download-link`、`GET /download/backup/<合言葉>`、
`DELETE /api/backup/file`、`PUT /api/backup/upload`(zip をそのまま送る)、`POST /api/backup/restore`(取り出して準備)、`POST /api/backup/cancel`、`POST /api/backup/ack`、`DELETE /api/backup/undo`。
一度に 1 つの操作だけ(409 `backup_busy`)。

  DB の検査(トリガー・ビュー・`../` を含む置き場・壊れた DB)、入れ替え(成功・途中の失敗で巻き戻し・準備だけの印)、**往復**(確定ページ + 設定 + 世代 → バックアップ → リセット → 復元 → 次の起動で、
  DB の全テーブルとファイルのハッシュが元と一致し、世代の組の照合を通る)、認識・学習の最中は拒否、状態にパス・値が出ない。
- E2E ㉟〜㊲(`web/e2e/backup.spec.ts`): 作成 → 保存(ダウンロード)→ 選ぶ → 要約 → 準備 → 取り消し、zip でない/書き換えた zip の拒否、アクセシビリティ。
- 実機でしか確かめられないもの(WebView2 の保存ダイアログ・実データの量・時間)は `docs/windows_checklist.md` の H。

## 限界

- 暗号化・署名はしない。ファイル一覧のハッシュは、壊れ・うっかりの書き換えを検出するもので、**悪意のある作成者が一覧ごと作り直した zip は防げない**(そのため、名前・DB のスキーマ・置き場の形・上限で、取り込んだあとに害を及ぼせないようにしている)。
- 大きなデータ(数 GB)では、作成・検査・取り出しに数分かかる(進捗を出す)。取り出しにはバックアップと同じだけの空き容量が要る。
- バックアップの作成中にデータが変わっても、DB は一点の整合したスナップショットだが、ファイル(切り出し画像など)は少し後の状態を含みうる(復元後に画像のないセルは「画像なし」と出る)。
