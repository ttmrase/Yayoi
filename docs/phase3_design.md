# Phase 3 設計案: 確認 UI とローカルサーバ

状態: **設計案(承認待ち。実装は承認後に始める)**。director の前提・要件(報告3 への返答)を反映。
関連: `docs/recognition.md`(認識の出力・要確認の理由コード)、`docs/layout.md`(セル切り出し)。

## 0. 前提と目標

- **前提**: 初期は、ほぼ全セルが要確認になる(合成データでの最終ホールドアウトで、空欄を除く要確認率は適応済みの重みで 75%、
  日付 95%・金額 90%・摘要 81%・科目 34%)。したがって UI の成否は「**1 ページの確認にかかる時間**」で決まる。
- **目標**: 1 ページ(29 行)を **数分以内**。初期(適応前)は 4 分以内、書き手への適応が効いた後は 2 分以内(根拠は §1)。
- **指標**(UI が計測して学習画面に出す。値の内容は記録しない): ページあたりの確認時間、セルあたりの滞在時間、修正したセルの割合、
  Enter だけで通過したセルの割合、候補の採用率、元に戻した回数。
- **対象外**: 認識・追加学習・CSV 形式の中身は Phase 2 / 4 / 5。Phase 3 は、それらを呼び出す口(API)と画面を作る。

## 1. 1 ページの確認時間の見積りと、それを実現する操作の流れ

1 ページ 116 セル(29 行 x 4 列)のうち、空欄を除く約 76 セル(最終ホールドアウトの平均)を見る。

| 操作 | 想定時間 | 根拠(KLM 風の見積り。実測で置き換える) |
|---|---|---|
| 正しいセルを確認して Enter | 0.8 秒 | 視線の移動と比較 0.6 + キー 0.2 |
| 誤ったセルを上書き(数字・短い語) | 4 秒 | 誤りに気づく 1 + 全選択して入力(5 字 x 0.25)+ Enter |
| 候補から選ぶ(Alt+1〜9) | 2 秒 | 候補を見て選ぶ |
| 拡大表示した金額の確認 | +0.4 秒 | 末尾の「-」/ 数字の見分け |

- 適応済みの重みの値の正解率(空欄を除く)は 0.63 なので、1 ページの誤りは約 28 セル:
  確認 76 x 0.8 + 修正 28 x 4 ≈ 61 + 112 ≈ **173 秒(約 2.9 分)**。素の重み(正解率 0.47)では約 3.7 分。
  ページ送り・拡大・迷いの上乗せ(+30%)を見ても、初期は 4 分以内に収まる想定。
- 書き手への適応で正解率が 0.9 に上がれば、誤りは約 8 セルで ≈ 61 + 30 ≈ 91 秒(**約 1.5 分**)。曲線の実測は「実現性の検証」(別報告)で更新する。
- したがって UI は **「正しいセルは Enter だけ」「誤りは入力か Alt+数字だけ」を最短にする**。マウスを使う操作を通常の流れに入れない。

### 基本の流れ(行モード)

1. ページを開くと、先頭行の先頭の要確認セルにフォーカスが当たっている。
2. 各行は 1 行の帯として、**切り出し画像(セルの実画像)と、その下(または右)に読み取り値(入力済みの入力欄)**を 4 列並べて表示する。
3. 正しければ **Enter**(次のセルへ)。誤っていれば、そのまま打ち込んで上書き(フォーカスしたとき値は全選択)→ Enter。
4. 行末の Enter で次の行の先頭へ。最後のセルの Enter で「ページを確定」の確認が出て、もう一度 Enter で確定して次のページへ。
5. 〃・年の継承・矢印・波線で展開した値には **「展開済み」バッジ**(種類つき: 〃 / 年 / → / 〜)を出す。バッジを押すと参照元のセルをハイライトする。

## 2. アーキテクチャ

```
 pywebview ウィンドウ(WebView2 = Chromium)
        │  http://127.0.0.1:<ランダムなポート>/#token=<起動時トークン>
        ▼
 FastAPI(uvicorn、スレッド)── 静的ファイル(Vite のビルド成果物。アプリに同梱)
        │                    ── REST + 進捗ストリーム(認証必須)
        ├─ SQLite(ジョブ・ページ・セル・確定履歴・出力履歴・設定・世代)
        ├─ 画像置き場(YAYOI_PRIVATE_DATA 相当のユーザーデータ領域。コミットしない)
        └─ 認識ワーカー(別プロセス。PyTorch。ページ単位のキュー。UI を止めない)
```

- **ジョブ**: 取り込んだ 1 まとまりのファイル(PDF・画像)。ページ = 画像 1 枚。ジョブの処理はページ単位のパイプライン:
  取り込み → 向き補正 → レイアウト(Phase 1)→ 認識(Phase 2)→ 確認待ち。認識は先読み(開いているページの次の 2 ページまで)で、確認中に待たせない。
- **ワーカー分離**: 認識(PyTorch)は別プロセスにして、重みの世代切り替え(Phase 4)やクラッシュが UI を巻き込まないようにする。
- **自動保存**: セルの編集のたびに(300 ms デバウンスで)サーバへ送る。サーバが SQLite に書く。クライアントは楽観的に更新し、失敗時は再送。
  中断・再開: 最後に開いたジョブ・ページ・セルを保存し、再起動後に同じ位置へ戻る。
- **データモデル**(`models.py` を拡張): `jobs`、`pages`(状態: 処理中 / 確認待ち / 確認中 / 確定)、`cells`(認識値・確定値・展開の由来・理由コード・
  確認済み・修正済み)、`edits`(元に戻す用の履歴)、`exports`、`generations`(Phase 4)、`settings`。実データの値はログに出さない。

### API(すべて `Authorization: Bearer <トークン>`)

| メソッド・パス | 内容 |
|---|---|
| `POST /api/jobs` | ファイルの取り込み(ローカルパスまたはアップロード)。ジョブ ID を返す |
| `GET /api/jobs`, `GET /api/jobs/{id}` | 一覧・進捗(処理中ページ数、確認待ち、確定) |
| `GET /api/pages/{id}` | ページの全セル(認識値・理由コード・候補・展開の由来・状態) |
| `GET /api/pages/{id}/cells/{cell}/image` | セル画像(レスポンスは画像バイナリ。`fetch` → blob URL で表示) |
| `PATCH /api/pages/{id}/cells/{cell}` | 値の更新・確認済みの印・候補の採用(リビジョンつき) |
| `POST /api/pages/{id}/undo`, `/redo` | 元に戻す・やり直し |
| `POST /api/pages/{id}/confirm` | ページの確定(サーバ側で条件を再検証。学習用の確定セルを記録し `learning.confirm_page` を呼ぶ) |
| `POST /api/pages/{id}/layout/approve` | 「境界は合っている」の承認 |
| `POST /api/pages/{id}/layout/adjust` | 罫線の補正(線の位置)→ 再切り出し・再認識 |
| `GET/PUT /api/settings` | 設定(§6) |
| `POST /api/exports/validate`, `POST /api/exports` | 出力の検証・実行 / `GET /api/exports` 履歴 |
| `GET /api/learning/generations`, `POST …/rollback`, `POST …/reset` | 世代・ロールバック・リセット(Phase 4 まではダミー) |
| `GET /api/events` | 進捗のストリーム(`fetch` のストリーム読み。`EventSource` はヘッダーを付けられないため使わない) |

## 3. 確認画面(§1 の流れの詳細)

### 3.1 キー操作

| キー | 動作 |
|---|---|
| Enter | このセルを確認済みにして次へ(要確認でないセルは飛ばさない。次の行の先頭まで順に進む) |
| 文字入力 | 値を上書き(フォーカス時に全選択。日付・金額は半角のみ受け付け、全角は半角に直す) |
| Shift+Enter / ↑ | 前のセルへ / 上の行の同じ列へ |
| Alt+1〜9 | 候補の n 番目を採用(候補一覧はフォーカス中のセルの下に番号つきで常時表示) |
| Ctrl+Z / Ctrl+Y | 元に戻す / やり直し(ページ内の全編集が対象。サーバの `edits` に残る) |
| Esc | このセルの編集を認識値に戻す |
| Ctrl+L | 行モード ↔ 列モード |
| Space | 切り出し画像の拡大を切り替え(金額は既定で拡大) |
| Ctrl+Enter | ページを確定(§3.3 の条件を満たすとき) |

WebView2 は Alt+数字・F キーなどを奪うことがあるので、Windows 実機でのキー操作の試験を M1 の完了条件に入れる。

### 3.2 表示

- 切り出し画像は layout の `CellCrop.color`(正準解像度)。**金額欄は拡大**(高さ 2 倍)して、末尾の「-」/ 数字が見分けられるようにする。
- 理由コードは短いラベルで出す(`row_inconsistent` → 「行の整合」など)。実データの値は理由に含まれない。
- 〃・年・矢印・波線の展開は、値の隣に **「展開済み」バッジ**。矢印・波線は候補(科目一致 > 金額一致 > 近さ)をバッジのメニューに並べる。
- **末尾「-」の両仮説で値が 10 倍違う**(`dash_digit_ambiguity`)場合は、金額セルを赤の枠にして「500 か 5000 か」と両方の値を並べて表示し、
  どちらかを明示的に選ぶまで確認済みにできない(Enter では進めず、Alt+1 / Alt+2 で選ぶ)。強い警告を、他の警告と見分けがつくようにする。

### 3.3 安全策: 要確認セルの通過とページの確定

- **「通過した」の定義**: そのセルにフォーカスが当たり、切り出し画像の読み込みが終わっている状態が 250 ms 以上続いた(連打で飛ばせない最小時間)。
  Enter の連続送りで自然に満たせる。マウスやタブで飛ばしたセルは通過に数えない(戻って通過させる)。
- **ページを確定できる条件**(UI で無効化し、**サーバでも再検証**): (1) 要確認の付いたセルがすべて通過済み、(2) 検証エラー(cp932 で表現できない文字・
  摘要の長さ・日付や金額の文法違反・`dash_digit_ambiguity` の未選択)が 0 件、(3) 行の整合ルール(金額あり + 他列 blank など)の警告が確認済み。
- 画面上部に **進捗バー**(通過済み / 要確認、残りの検証エラー数)。残りの要確認セルへ `N` キーで飛べる。
- ページ確定後は取り消せる(確定の取り消しは「ページ再オープン」。学習への反映は Phase 4 で世代と結びつける)。

### 3.4 行モードと列モードの比較

| | 行モード(既定) | 列モード |
|---|---|---|
| 表示 | 1 行 = 4 列を横に並べた帯。紙と同じ並び | 1 列のセルだけを縦に並べる(例: 日付の列だけ 29 件) |
| 長所 | 行の文脈(〃の参照元、摘要から金額の見当、行の整合ルール)がそのまま見える。紙の読み方に近く、迷いが少ない | 同じ種類の字を続けて見るので目が慣れる。系統的な誤り(0 と「-」、年の継承ミス)に気づきやすい。キー入力のモード切り替えが無く、日付・金額は半角数字だけを打ち続けられる |
| 短所 | 列ごとに入力の種類(日付は数字、摘要は日本語)が変わり、IME の切り替えが要る | 行の文脈が見えない(摘要の内容から金額の誤りに気づけない)。〃の展開を確認するには参照元へ戻る必要がある |
| 向く場面 | 既定。初期(誤りが多い時期) | 精度が上がった後の日付・金額の一括確認。同じ書き手の長い連続ページ |

- 両モードは同じデータ(同じセル・同じ通過の記録)を見ているので、いつでも切り替えられる。切り替え時はフォーカス中のセルを保つ。
- 列モードの単位は「列全体(29 件)」。**確定の条件は列モードでも同じ**(要確認セルの通過)。実測(§7 のタイミング計測)で既定を見直す。

## 4. レイアウトの確認・補正

- レイアウトの状態(`PageStatus`、理由コード `band_clipped` / `ruled_lines_low` など)をページの上部に表示。要確認のページは、認識結果より先にこの確認を求める。
- **「境界は合っている」**: 重ね表示(罫線の検出位置を元画像に重ねる)を見て、ワンクリック(または `Y`)で承認。承認したページは認識の要確認フラグが外れるのではなく、
  「レイアウト由来の要確認」だけが外れる。
- **罫線のドラッグ補正**: 水平・垂直の罫線をドラッグして動かし、「再切り出し」で `layout` を手動指定の罫線で再実行する
  (依存: `layout.pipeline` に「罫線位置の上書き」を受け取って再切り出しする入口を足す。Phase 3 の M3 で実装)。

## 6. 設定画面

保存先は SQLite の `settings`(JSON)。入力のたびに検証し、不正な設定では出力を実行させない。

- **支払手段 → 貸方科目・補助科目**(行の追加・削除)。科目の語彙は認識の「科目の閉じた語彙」(`JobContext.accounts`)に使う。
- **タイトル → 借方科目**(帳票のタイトルごと)。
- **事業者区分・課税方式・経理方式**(選択式。弥生のインポート形式で必要な値は Phase 5 で確定)。
- **科目ごとの既定の税区分**(表で編集)。
- 設定の変更は、すでに確定したページには遡らない(出力時に現在の設定を使う)。出力画面に「使用した設定のスナップショット」を残す。

## 7. 出力画面

- **形式の選択**(弥生のインポート形式。種類は Phase 5 で確定)、対象ページ(確定済みのみ)の選択、**検証**(cp932・長さ・必須項目・日付の範囲・金額 > 0・
  科目や税区分の未設定)。検証エラーはセルへのリンクで確認画面に戻れる。
- **出力の履歴**(日時・形式・対象ページ・件数・ファイルのハッシュ。値は載せない)。
- **重複出力の警告**: ページ(画像のハッシュ + 確定値のハッシュ)が過去に出力されていれば警告し、明示的な承諾が無ければ出力しない。

## 9. セキュリティ

- **127.0.0.1 だけにバインド**。ポートは起動ごとにランダム。**起動ごとのランダムなトークン**(`secrets.token_urlsafe(32)`)を全 API で必須にする
  (静的ファイル以外)。トークンは URL の **フラグメント**(`#token=…`)で pywebview の初期 URL に渡す(サーバには送られず、ログにも残らない)。
  JS が読み取り、メモリにだけ保持して(localStorage には置かない)フラグメントを消し、`Authorization: Bearer` で送る。
- **Host ヘッダーの検証**: `127.0.0.1:<port>` と `localhost:<port>` 以外は 400(DNS rebinding 対策)。`Origin` が付いていれば同じオリジンのみ許可。
- **CORS は許可しない**(`Access-Control-*` を一切返さない)。同一オリジンで配信するので不要。プリフライトにも応答しない。
- セル画像は `<img src>` ではトークンを付けられないので、`fetch` + blob URL で表示する(URL にトークンを載せない)。進捗もヘッダー付きの `fetch` ストリーム。
- **外部リソースを読み込まない**: CDN・Web フォント・外部のスクリプトを使わない。Vite のビルド成果物とアイコンをすべてアプリに同梱する。
  `Content-Security-Policy: default-src 'self'; img-src 'self' blob:; connect-src 'self'; frame-ancestors 'none'`。
  テストで、ビルド成果物に `http://` / `https://` の外部 URL が無いことを検査する(`docs/dependencies.md` に npm 依存のライセンスを記録)。
- ログに実データ(認識値・確定値・ファイル名)を出さない。エラーは理由コードと ID だけ。
- 画像・DB は `YAYOI_PRIVATE_DATA` 相当のユーザーデータ領域にだけ置く(コミットしない)。

## 10. フロントエンドの技術

- **React + TypeScript + Vite を採用**(既定のまま)。理由: 確認画面は状態(セルごとの値・通過・元に戻す・フォーカス)が複雑で、
  型つきのコンポーネントと小さな状態管理(Zustand 程度)が保守しやすい。Playwright・Testing Library との相性がよく、候補の人材・資料も多い。
  29 行 x 4 列の画面なので、仮想化は要らない。
- 代替: Svelte(小さく速いが、チームの慣れと周辺の資料が少ない)/ Preact(React 互換でさらに小さい。必要になれば `preact/compat` で置き換え可能)/
  サーバ描画 + htmx(ビルドが不要だが、キー操作中心の複雑なクライアント状態を扱いにくい)。上記を比べた結果、React を既定とする。
- Node は**開発・CI のビルド時だけ**必要。`npm ci`(ロックファイルで固定)→ `vite build` → 成果物を `src/yayoi_ocr/web/static/` に置き、wheel に同梱する。
  利用者の環境に Node は要らない。
- フォントは OS のシステムフォント(`"Yu Gothic UI", Meiryo, sans-serif`)を指定するだけで、フォントファイルを読み込まない。

## 11. テスト

- **Playwright(端から端まで)**: 合成のジョブ(`synth` でページを作り、**テスト用の認識器**が正解に決まった誤りを混ぜた結果を返す)を取り込み、
  確認 → 確定 → 出力まで。torch を使わないので CI(Windows / Ubuntu)で動く。torch を使う実認識の E2E は `slow` マーカーで別に用意する。
  シナリオ: ① Enter だけで 1 ページを通す、② 誤りを上書き / Alt+数字で候補採用、③ 要確認セルを飛ばして確定しようとして拒否される、
  ④ 10 倍違いの金額で明示選択が要る、⑤ 列モードへ切り替えて続行、⑥ 元に戻す、⑦ 中断 → 再起動 → 同じ位置で再開、⑧ レイアウトの承認・罫線補正、
  ⑨ 設定 → 出力の検証エラー → 修正 → 出力、⑩ 同じページの重複出力の警告、⑪ 学習画面の世代・リセット。
- **セキュリティテスト(pytest)**: トークン無しは 401、誤った Host は 400、CORS ヘッダーが返らない、静的ファイルに外部 URL が無い、
  ログに値が出ない(固定の合成値で検査)。
- **計測テスト**: Playwright で「Enter だけで 1 ページ(116 セル)」の所要時間と、「誤り 28 セルを修正」の所要時間を測り、§1 の見積りと比べる(回帰の目安)。
