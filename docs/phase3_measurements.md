# Phase 3 の計測(開発機での基準値)

開発機(Linux コンテナ・4 コア・**別の重い計算が同時に走っている不利な条件**、Chromium)での機械計測。実際の PC(Windows・WebView2)での値は
`docs/windows_checklist.md` の手順で測り直す。**すべて合成データ**(実データは使っていない)。

## 1. 操作の遅延(`web/e2e/perf.spec.ts`、29 行 × 4 列 = 116 セルの合成ページ)

| 計測 | p50 | p95 | 備考 |
|---|---|---|---|
| Enter → 次のセルにフォーカス(キー入力から次のフレームまで) | 7 ms | 13 ms | 保存は待たない(楽観的に進み、保存は順序どおりに送る) |
| ページを開く(ボタン → 先頭 8 枚の切り出し画像が出るまで) | 324 ms(1 回) | | 画像は表示するセルから遅延読み込み |
| サーバ GET /api/pages(116 セル) | 48 ms | 59 ms | 同時の重い計算(負荷平均 14 / 4 コア)の影響を含む |
| サーバ PATCH(セルの保存) | 56 ms | 64 ms | 〃 |

人の操作(0.3 秒/セル以上)に比べて、アプリの遅れは無視できる(1 セルあたり約 30 ms を含めた実測 = 32 セルを 10.5 秒)。

## 2. 認識(別プロセス、合成ページ 3 枚)

- 1 ページ 約 6〜8 秒(layout 約 4 秒 + 認識 約 3 秒 + 画像保存 0.2 秒)、ジョブ開始から最初のページが確認待ちになるまで 約 12 秒(プロセス起動・torch 読み込みを含む)。
- torch のスレッド数を全コアにすると他の処理と取り合って 34〜44 秒/ページに悪化するので、論理コアの半分(2〜4)に制限(`YAYOI_TORCH_THREADS` で固定可)。
  通常の PC での値は Windows 実機で測り直す(F1)。

## 3. 安全策の検証(要確認セルを飛ばせないこと)

- **Enter の連打・キーリピートで要確認セルを通過できない**(M5 で M1 の実装漏れを発見して修正): 画面は 250 ms 見ていないセルへの Enter を無視し、サーバも
  値を直さない Enter が前の通過から 250 ms 以内なら「通過」に数えない。E2E ⑳(5 ms 間隔で 40 回の連打 → 通過は半分未満・確定不可)、pytest(10 ms 間隔の連打は先頭 1 つだけ通る)。
- 要確認を飛ばしたまま確定できない(UI・サーバ)、10 倍違いの金額は明示して選ぶまで確認済みにならない(UI・サーバ)、確定の条件のサーバ再検証。

## 4. アクセシビリティ(`web/e2e/a11y.spec.ts`、axe-core 4.10.3・WCAG 2.0/2.1 A・AA)

ジョブ・確認(行モード・列モード)・罫線の確認・補正・設定・出力・学習の各画面で、**重大・深刻な違反 0 件**。
見つけて直したもの: 行番号の文字色のコントラスト不足、`role="grid"`(子の行・セルのロールが無い)→ `group`、罫線パネルの `role="img"` の中の操作要素(入れ子の操作要素)→ `group`。
キーボードだけで全画面を操作できる(罫線の隅の丸は矢印キーで動かせる)。`<html lang="ja">`。実機のスクリーンリーダー(NVDA 等)での確認は未実施。

## 5. 確認時間の見積り(§0・§1)との対応

見積り(初期 約 3〜4 分/ページ、適応後も約 2 割のセルを直す)は**人の操作時間の仮定**で、機械計測ではアプリの遅れが無視できることまでしか言えない。
1 ページの時間は、おおよそ 要確認セル数 × (見る時間 ≥ 0.25 秒 + 読む時間)+ 直すセル数 × (入力 2〜3 秒)+ ページの切り替え で決まる。
合成ページの要確認率は非空欄セルの約 75〜90%(科目の語彙が空の間は科目列が全て要確認)。実際の値は Windows 実機で測る(`docs/windows_checklist.md` の G)。
