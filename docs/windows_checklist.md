# Windows 実機チェックリスト(Phase 3 の確認 UI)

開発機(Linux・Chromium)では確かめられない項目の一覧。**実機の担当者(利用者)が、実データを使わないテスト用の画像(合成帳票)で行う**。
結果を報告するときも、画面・画像・ファイルに実データの内容が写らないようにする(合否と気づきだけを書く)。

- 前提: Windows 10 / 11、WebView2 ランタイム(Windows 11 は標準。Windows 10 は未導入のことがある)、Python 3.11 以上。
  配布形式(インストーラ)は Phase 6。それまでは `pip install -e .[app,desktop]` と、重み・フォントの取得(`scripts/fetch_models.py`・`fetch_fonts.py`)で動かす。
- 起動: `yayoi-ocr app`(ウィンドウが開く)。開発専用に `yayoi-ocr app --dev --no-window --backend fake` でブラウザからも開ける(URL にトークンが出るので、共有 PC では使わない)。
- データの置き場所: `%LOCALAPPDATA%\yayoi-ocr`(DB・取り込んだファイル・切り出し画像・出力ファイル)。

### 弥生での取り込み試験(E6・E9。**利用者の PC で行う**)

アプリが出す CSV を、実際の弥生(やよいの青色申告 25)が受け付けるかの試験。**取り込みは元に戻せない**ので、必ず「テスト用の事業所データ」(弥生で新しく作った試験用)、
または本番のデータを**弥生でバックアップしたあと**に行う。実帳票は使わず、アプリが作る**架空の 2 行**のサンプルで確かめる。

準備:
1. 弥生で、試験用の事業所データを作る(または本番データのバックアップを取る)。その会計期間・事業者区分(課税/免税)・消費税の経理方式(税込/税抜)を、アプリの設定と同じにする。
2. アプリの「設定」(初期設定ウィザード)で、**弥生に登録してある名前そのまま**に入力する: 支払手段の貸方科目・補助科目、タイトルの借方科目・補助科目、科目ごとの既定の税区分(候補から選ぶ)。
   弥生側に無い補助科目を使うと、取り込みのときにマッチングリストが出る(補助科目は新規作成される)。

E6(弥生インポート形式):
1. アプリの「出力」→ 形式を「弥生インポート形式」にして、「弥生の取り込み試験用のサンプル(架空の 2 行)」を開く。日付を**試験用データの会計期間内**にして「サンプルをダウンロード」(`sample_yayoi_import.csv`)。
2. 弥生で 仕訳日記帳 →「インポート」(ファイルの形式は、弥生インポート形式)でそのファイルを選ぶ。**Excel では開かない**。
3. 期待: エラーなく 2 件取り込まれる。**マッチングリストが出ない**(出たら、その科目・補助科目・税区分の名前が弥生の登録と違う → 設定を直す)。日付・借方/貸方の科目と補助科目・税区分・金額・摘要が、サンプルのとおり。
4. 税抜経理の設定のとき: 借方税金額(内税の行)が入っている。外税・別記の税区分を選んだときは、税額が空で取り込まれる(弥生側で入力する)。
5. 結果(OK/NG、マッチングリストの有無、気づいた点)を開発者に連絡する(画面の写真は、架空のサンプルなので送ってよい)。

E9(スマート取引取込):
1. 形式を「スマート取引取込」にして、同じ手順でサンプルをダウンロード(`sample_smart_torihiki.csv`。1 行)。
2. 弥生の スマート取引取込 →「CSV ファイル取込」で選ぶ。取引手段(科目 + 補助科目)を 1 つ選ぶ。
3. 期待: 1 件取り込まれる。日付が西暦 4 桁で正しい。相手の科目は弥生が摘要から推測する(タイトルの借方科目は反映されない — 画面にもそう書いてある)。

## F'. 追加学習(Phase 4。バックグラウンドの学習・世代の管理)

試用版で初めて、利用者の PC で学習が動く。合成データ(架空の帳票)の確定済みページを 6 ページ以上たくわえてから確かめる(学習画面「追加学習」の「今すぐ学習する」)。
確認するのは動作と負荷で、**実帳票の内容は記録しない**。

| # | 確認 | 期待 |
|---|---|---|
| T1 | 「今すぐ学習する」を押す | 進み具合が出て、数分〜十数分で「採用 / 不採用 / 見送り」が理由つきで出る。時間(CPU の機種)を記録する。失敗なら理由コードを記録 |
| T2 | 学習中のタスクマネージャ | 学習プロセス(`python.exe` の `train_worker`)の優先度が「通常以下」。CPU 使用率が全コアを使い切らない(論理コアの半分、2〜4 スレッド)。メモリが数 GB に増え続けない |
| T3 | 学習中に確認画面を操作する(Enter の連続・IME の変換) | キー入力の反応が遅れない。認識(新しいジョブ)も止まらない |
| T4 | 学習中にアプリを閉じて開き直す | 学習は止まり、次の起動で学習画面の前回の結果が「中断(アプリが閉じられたため)」になる。作業フォルダ(`%LOCALAPPDATA%\yayoi-ocr\training`)に確定値を含む計画ファイルが残らない |
| T5 | 学習中にタスクマネージャで学習プロセスを強制終了 | アプリは落ちない。前回の結果が「失敗(学習のプログラムが異常終了しました)」になり、使用中の世代は変わらない |
| T6 | 採用された世代がある状態で、新しいジョブを認識する | 認識できる(重み・確信度が読める)。学習画面の世代の表で、その世代の「認識したページ」が増える。「この世代に戻す」→ 新しいジョブ → 世代 0 で認識される |
| T7 | 「出荷時の重みに戻す(リセット)」(確定データを残す / 切り出し画像と学習状態も削除する) | 残す: 切り出し画像が見える・次の学習の元になる。削除: 切り出し画像が消え、`%LOCALAPPDATA%\yayoi-ocr\pagedata` の `.npz` が消える |
| T8 | GPU のある PC(あれば) | 学習のデバイスが cuda になる(精度レポートの世代の `device`)。**GPU の経路は開発機(CPU のみ)で未検証**。動かない場合は環境変数 `YAYOI_TRAIN_DEVICE=cpu` で CPU に固定できる(起動前に設定) → 報告する |
| T9 | ディスク使用量 | `pagedata` は 1 ページ数百 KB。100 ページで数十 MB。世代の重みは 1 世代あたり約 70 MB |

## G. 確認時間の実測(設計 §1 の見積りの置き換え)

合成帳票 3 ページ以上を、利用者が普通に確認するときの**ページあたりの時間**を、学習画面の「1 ページの確認時間(中央値)」と手元の計時で記録する。
(画面は確認時間を内部で計る。値の内容は記録しない。)

- 記録するもの: 初回 3 ページ / 以降 10 ページの中央値、直したセルの割合(学習画面)、困った操作。
- 見積り(§0): 初期 約 3〜4 分/ページ、適応後も約 2 割のセルは直す。実測がこれを超える場合は、どの操作(キー・IME・スクロール・画像の見づらさ)が時間を使っているかを書く。
